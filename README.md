
## Задание
repository for the test assignment Tatlin.Unified DataPath 

Устройство хранения данных типа лента (Tape) предназначено для последовательной записи и чтения данных. Считывающая/записывающая магнитная головка неподвижна во время чтения и записи, а лента имеет возможность двигаться в обоих направлениях. Запись и чтение информации возможны в ячейку ленты, на которой в данный момент находится магнитная головка.

Перемещения ленты – затратная по времени операция – лента не предназначена для произвольного доступа.

Имеется входная лента длины N (где N – велико), содержащая элементы типа integer (232). Имеется выходная лента такой же длины. Необходимо записать в выходную ленту отсортированные по возрастанию элементы с входной ленты. Есть ограничение по использованию оперативной памяти – не более M байт (M может быть < N, т.е. загрузить все данные с ленты в оперативную память не получится). Для реализации алгоритма можно использовать разумное количество временных лент, т.е. лент, на которых можно хранить какую-то временную информацию, необходимую в процессе работы алгоритма.

Необходимо создать проект С++, компилируемый в консольное приложение, которое реализует алгоритм сортировки данных с входной ленты на выходную.

Необходимо сделать следующее:

Определить интерфейс для работы с устройством типа лента.
Написать класс, реализующий этот интерфейс и эмулирующий работу с лентой посредством обычного файла. Должно быть возможно сконфигурировать (без перекомпиляции – например, через внешний конфигурационный файл, который будет прочитан на старте приложения) задержки по записи/чтению элемента с ленты, перемотки ленты, и сдвига ленты на одну позицию.
Файлы временных лент можно сохранять в директорию tmp.
Написать класс, реализующий алгоритм сортировки данных с входной ленты на выходную.
Консольное приложение должно принимать на вход имя входного и выходного файлов и производить сортировку.
Желательно написать юнит-тесты.



## Сборка проекта
Для сборки проекта необходим компилятор с поддержкой C++17 и CMake.

```bash
mkdir build && cd build
cmake ..
make
```

Пользователю нужно знать формат `config.txt`.
Параметры работы эмулятора ленты настраиваются в файле `config.txt`. Если файл отсутствует, используются значения по умолчанию.

Пример `config.txt`:
```ini
memory_limit_bytes=67108864  # Максимальный объем RAM (64 МБ)
read_delay_ms=10            # Задержка чтения одного элемента
write_delay_ms=10           # Задержка записи одного элемента
move_delay_ms=5             # Задержка сдвига ленты на 1 позицию
rewind_delay_ms=100         # Задержка полной перемотки
```

### Подробности алгоритма
Для внутренней сортировки используется поразрядная сортировка, она всегда работает за линейное время, и требует доп памяти `N`

В качестве алгоритма внешней сортировки была выбрана сортировка слиянием. Сначала исходная лента делится на k частей. Каждая часть сортируется внутренней сортировкой. Потом эти части сливаются в одну. Сливать по 2 файла - долго.
Поэтому мы за раз открываем `kMaxOpenTempTapes = 32` файла из каждого берём по числу и добавляем в очередь с приоритететами, где в качестве приоритета берём значение числа. Затем минимум записыывам в файл. Добавляем элемент из той очереди из которой только что пеерписали в итоговый файл.
Получаем `log_k(число файлов)` слияний.

Пусть надо отсортировать 50'000'000 чисел, а в памяти мы можем зранить не более 100. Тогда лента разобъём на k = 500'000 частей. Создание k файлов и хранаие их на диске - дорого и неоптимально. Поэтому как только мы записали на диск kMaxOpenTempTapes файлов, мы их сливаем в файл уровня + 1.
Так на диске в худшем случае будет храниться `kMaxOpenTempTapes-1` на каждом из `log_kMaxOpenTempTapes(число файлов)`.

После слияния всех начальных файлов. сливаем все файлы которые остались пока не останется один файл на верхнем уровне. Далее это файл переписывается на выходную ленту.
(Вообще можно сделать перемещение + переименование файла с результатом)


### Расчет использования памяти


Считается, что за раз можно открыть 32 ленты `kMaxOpenTempTapes = 32`.

А в памяти хранить не менее  `kMinElementLimit = 1024`(4кб данных + 4кб на radix sort).

Считаем kElementLimit. Память в байтах делим на `sizeof(int32_t)`, делим на 2 и умножаем на 3/4 чтобы доп расходы вписывались в память. Для читабельности будм делить на 11.
``` C++
uint64_t kElementLimit = std::max<uint64_t>(
      kMinElementLimit, (FileTape::global_config.memory_limit_bytes / 11));
```

Если памяти хваатет чтобы поместить все числа в памятть и отсортиовать, то делаем так.

Если в память нельзя поместить все числа, то тогда при расчёте количества элементов в памяти учитываем что максимум одновременно откроем не более kMaxOpenTempTapes файлов, каждый из которых в пике будет потерблять примерно 10кб байт. И для внутренней сортировки которая будет использоватся для сортировки маленьких файлов под данные 8 кб минимум


Для внешней сортировки считаем примерный минимум 512кб под данные и файловые потоки в памяти. Для внутренней - 8кб.



## Структура проекта
- `TapeInterface.hpp` — абстрактный интерфейс ленты.
- `FileTape.hpp/cpp` — реализация ленты на базе файлов с эмуляцией задержек.
- `TapeSorter.hpp/cpp` — логика внешней сортировки (Merge Sort + Radix Sort).
- `TapeConfig.hpp` — загрузчик конфигурации.
- `main.cpp` — точка входа, парсинг аргументов командной строки.

## Ограничения и допущения
*   Временные файлы создаются в папке `tmp` относительно текущей рабочей директории.
*   Программа автоматически удаляет временные файлы после завершения работы и папку `tmp`
*   Формат данных на ленте: бинарный, последовательность `int32_t`.
*   Изменение минимального числа элементов и кол-ва одновременно открытых файлов требует перекомпиляции программы
